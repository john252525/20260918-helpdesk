# Архитектурные решения

Формат: контекст → решение → последствия. Читай перед тем, как предлагать изменения в этих областях.

---

## ADR-001: API-first, фронтенд как отдельный клиент

**Контекст.** Нужен интерфейс для операторов, но в перспективе возможны мобильное приложение, бот, интеграция с CRM.

**Решение.** Бэкенд — чистый REST API, ничего не знает о фронтенде. Интерфейс — статичный SPA, обращается только к API.

**Последствия.** Любой новый клиент подключается без изменений в бэкенде. Фронтенд можно разложить на отдельном хостинге, сменить или переписать, не трогая сервер.

---

## ADR-002: PostgreSQL в отдельном контейнере, не системный

**Контекст.** На сервере уже работает системный PostgreSQL с базами других проектов. Сначала использовалась SQLite.

**Решение.** Свой контейнер `postgres:16-alpine`, порт `127.0.0.1:18401`, лимит памяти 256 МБ, том `helpdesk_pgdata`.

**Последствия.** Полная изоляция от чужих баз. SQLite отвергнут: при нескольких поллерах и вебхуках он блокирует всю базу на каждой записи. Наружу контейнер не смотрит, доступен только с сервера. Миграция заняла около 20 МБ памяти.

---

## ADR-003: SQL должен быть портируемым между SQLite и PostgreSQL

**Контекст.** Разработка началась на SQLite, боевая база — Postgres. При переезде обнаружились `strftime`, `julianday`, `printf` — их в Postgres нет, эндпоинт отдавал `500`.

**Решение.** Отказаться от диалект-специфичных функций. Где нужно — ветвление по диалекту через хелперы (`_duration_seconds`, `_bucket_expr` в `backend/app/services/metrics.py`).

**Последствия.** Миграция между базами стоит одну строку в конфиге. Пример правильной замены: `_last_messages` переписан с `max(id)` на оконную функцию `row_number() over`.

## ADR-004: Хронология по (created_at, id), не по id

**Контекст.** При импорте истории VK сообщения записывались пачками: сначала все входящие, потом все исходящие. Ответы получали большие `id`, хотя по времени были раньше. В диалоге показывалось «все входящие подряд, потом все исходящие».

**Решение.** Везде, где важен порядок — сортировка по составному ключу `(created_at, id)`. Касается списка сообщений, превью последнего сообщения, пагинации `before_id`.

**Последствия.** Порядок корректен для любого бэкфилла, включая вебхуки, пришедшие не по порядку. Ошибка была незаметна на живых данных, вылезла только на импорте.

## ADR-005: `EmailStr` не используется, свой валидатор

**Контекст.** Pydantic `EmailStr` через `email_validator` отвергает домены `.local` и `.internal` как зарезервированные. Bootstrap-админ `admin@helpdesk.local` не мог войти — `422` на логине. Войти в систему было невозможно никому.

**Решение.** Свой мягкий валидатор `_check_email`: требует ровно один `@`, непустые части, точку в домене. Без проверки доставляемости.

**Последствия.** Внутренние домены работают, мусор вроде `a@@b.com` и `x@.com` отклоняется. Формат в OpenAPI больше не помечается как `email` — это нормально для внутренней системы.

## ADR-006: `workspace_id = NULL` означает суперадмина

**Контекст.** Нужны роли: владелец платформы, админ компании, оператор.

**Решение.** `NULL` в `users.workspace_id` — суперадмин, не привязанный ни к одной компании. Остальные роли привязаны к конкретной.

**Последствия.** Изоляция выражается одним условием: `user.role != "superadmin" and row.workspace_id != user.workspace_id`. Суперадмин видит всё, остальные — только своё. Проверка прав на выдачу суперадмина: только суперадмин может создать другого суперадмина.

## ADR-007: Чужие данные отдают 404, а не 403

**Контекст.** Админ компании обращается к диалогу другой компании.

**Решение.** Ответ `404 Not Found`, а не `403 Forbidden`.

**Последствия.** Посторонний не может подтвердить существование объекта — не получит подсказки для перебора id. Единственный минус: при отладке сложнее отличить «нет доступа» от «не существует», но это приемлемо.

## ADR-008: Секрет в URL вебхука вместо номера канала

**Контекст.** Вебхуки вида `/webhooks/vk/2` перебираются: номера сквозные и предсказуемые, можно подсунуть данные в чужой канал.

**Решение.** URL стал `/webhooks/vk/{id}/{secret}`, где секрет — `secrets.token_urlsafe(24)`. При неверном секрете — `404`.

**Последствия.** Провайдеру не нужен заголовок авторизации, только непредсказуемый URL. Для VK это неважно (Long Poll), для WhatsApp и Email — обязательное условие подключения.

## ADR-009: Long Poll с сохранением курсора, Callback API отложен

**Контекст.** VK поддерживает оба способа. Long Poll не требует публичного HTTPS.

**Решение.** Long Poll, но с существенной доработкой: **курсор `ts` сохраняется в `Channel.config` после каждого опроса**. При старте читается оттуда.

**Последствия.** Раньше при каждом рестарте поллер начинал «с этого момента» и терял всё за время простоя — при десятке перезапусков за сессию это молча пропадало. Теперь VK досылает пропущенное (держит очередь несколько часов). Остаются два ограничения: поток на канал и лимит подключений к одной группе. При росте до 10–15 компаний переходим на Callback API.

## ADR-010: Ответ API честно сообщает о неприменённом статусе

**Контекст.** Оператор отправляет ответ и просит перевести диалог в «в ожидании». Провайдер недоступен, сообщение сохраняется как `failed`, а `mark_status` молча игнорировался. Клиент получал `201` и никакой информации.

**Решение.** Схема `MessageSentOut` расширена полями `status_applied` и `notice`. При неудачной доставке статус не применяется (клиент ответа не получил — переводить в «ждём клиента» нельзя), но об этом явно сообщается в ответе и в таймлайне событий.

**Последствия.** Клиент API никогда не остаётся в неведении. Ошибки доставки видны оператору всплывающим уведомлением.

## ADR-011: `dry_run` для тестов боевых каналов

**Контекст.** Smoke-тест отправлял сообщение реальному клиенту, потому что писал в живой канал. VK позволяет удалять свои сообщения, но не всегда и не мгновенно.

**Решение.** Параметр `?dry_run=true` на `POST /conversations/{id}/messages`: сообщение сохраняется в переписке, провайдеру не уходит.

**Последствия.** Логику ответа можно проверять без риска. Сквозную доставку гонять только на канале-заглушке.

## ADR-012: Проверки в git-хуке, не в CI

**Контекст.** Нужно не давать коммитить сломанный код и без обновления слоя памяти. Варианты: pre-commit хук локально, или CI на сервере (GitHub Actions и подобное).

**Решение.** Локальный `pre-commit` хук через `scripts/pre_commit.py`. CI не заводим.

**Последствия.** Проверка срабатывает мгновенно, до того как код ушёл. Нет внешних зависимостей — ни аккаунтов, ни настроенных раннеров. Минус: хук живёт в `.git/hooks/`, которая **не версионируется**, поэтому на новой машине нужен `scripts/install_hooks.py`. Минус второй: хук можно обойти через `--no-verify`, и это осознанно — обход задокументирован, потому что жёсткий запрет привёл бы к привычке коммитить в обход всегда.

**Когда пересмотреть.** Если появится несколько разработчиков или сервер сборки — добавить CI как вторую линию защиты. Хук останется первой.

## ADR-013: Обновление STATE.md — предупреждение, не блокировка

**Контекст.** Правило «после итерации обнови STATE.md» держится на дисциплине. Хук мог бы блокировать коммит, если код менялся, а STATE — нет.

**Решение.** Только предупреждение. Коммит проходит, но в выводе явно сказано, что следующий агент не узнает об изменениях.

**Последствия.** Не раздражает на мелких правках (опечатка, форматирование), где состояние проекта не меняется. Но напоминание видно каждый раз. Компромисс между «не работает вообще» и «бесит настолько, что коммитят в обход».

**Как проверить, что работает.** Если предупреждение стало появляться и исчезать бесследно, то есть все привыкли его игнорировать — надо переходить к жёсткой блокировке.

## ADR-014: Валидатор ссылок ищет файлы по имени, а не только по пути

**Контекст.** `scripts/check_docs.py` проверяет, что каждое упоминание файла
в документах ведёт на существующий файл. Первая версия разрешала путь от
корня проекта, папки документа и `backend/app`. Короткие упоминания вроде
`STATE.md` (реально лежит в `docs/memory/`) считались битыми — это блокировало
коммит по ложной причине.

**Решение.** Трёхшаговое разрешение:

1. Явные базы путей — покрывают полные и относительные ссылки
2. Поиск по имени файла во всём проекте (кроме `.venv/`, `.git/`, `data/`) —
   если имя уникально, ссылка валидна
3. Нигде не нашлось — настоящая ошибка

**Последствия.** Автор документа пишет `STATE.md`, а не
`docs/memory/STATE.md` — валидатор подстроится. При этом опечатка в имени
файла по-прежнему блокирует коммит: такого имени нет нигде в проекте.

**Принцип, который здесь зафиксирован:** инструмент проверки подстраивается
под то, как люди пишут, а не наоборот. Заставлять автора писать полные пути
ради валидатора — значит получить документы, оптимизированные под скрипт,
а не под читателя.

**Когда пересмотреть.** Если начнут появляться ссылки на файлы, которых в
проекте несколько (например, на конкретный `__init__.py`) — добавить
предупреждение о неоднозначности.

## ADR-015: Проверка ссылок различает путь и упоминание

**Контекст.** Валидатор `scripts/check_docs.py` проверял каждое имя файла в
обратных кавычках. Это ломало документацию: когда автор объясняет работу
самого валидатора, он **естественно** приводит пример несуществующего имени.
Трижды подряд такие примеры блокировали коммит.

Первая попытка решить — правилом «не писать имён несуществующих файлов в
документации». Провалилась: приведение примеров при объяснении проверки
слишком естественно, чтобы от него отказываться ради инструмента.

**Решение.** Валидатор различает две ситуации:

| Что в тексте | Как проверяется |
|---|---|
| Путь со слэшем | строго: файла нет → ошибка, коммит блокируется |
| Голое имя | если файла нет нигде → предупреждение, коммит проходит |

**Почему так.** Слэш означает, что автор указывает конкретное место в проекте —
это утверждение «файл здесь есть», и если его нет, документация врёт.
Голое имя чаще оказывается отсылкой или примером; если файл с таким именем
существует хоть где-то в проекте — ссылка валидна (см. ADR-014).

**Последствия.** Примеры в объяснениях больше не блокируют коммит. Настоящие
битые ссылки — блокируют, и это проверено. Предупреждение о ненайденном
голом имени остаётся видимым в выводе: если это не пример, а промах, автор
заметит.

**Принцип.** Инструмент проверки не должен заставлять автора менять стиль
изложения. Если правило требует писать неудобно — правило неправильное.

## ADR-017: Тесты восстанавливают файлы в finally

**Контекст.** Валидатор слоя памяти проверяется так: во временно
изменённый документ добавляется фрагмент, запускается проверка, документ
восстанавливается. Один прогон упал до отката — фрагмент остался,
следующий добавил поверх своего. `STATE.md` вырос с 48 до 308 строк.

**Решение.** Тест, пишущий в боевой файл, восстанавливает его в блоке
`finally`, а не в конце скрипта: падение не должно оставлять мусор.

**Надёжнее на будущее.** Писать тестовые фрагменты не в боевой файл,
а в копию во временной папке. Тогда откат не нужен. Отложено: валидатор
принимает только один набор документов, путь к ним зашит в модуле.

**Когда пересмотреть.** Как только валидатор научится принимать каталог
параметром — тесты переедут в `/tmp`, и этот ADR потеряет силу.

---

## ADR-018: Валидатор принимает каталог параметром, тесты работают на копии

**Контекст.** ADR-017 зафиксировал правило «тест восстанавливает файлы в
`finally`», но это лекарство от симптома. Корень проблемы был в том, что
тестам приходилось писать в боевые документы — иначе никак.

**Решение.** `scripts/check_docs.py` принимает аргумент `--root`, задающий
каталог проверки. Тесты (`scripts/test_check_docs.py`) работают на копии
проекта во временном каталоге и убирают его за собой.

**Последствия.** Тесты перестали быть источником мусора в рабочем дереве.
`STATE.md` и другие документы не трогаются при прогонах. ADR-017 сохраняет
силу для любых других тестов, которым всё же придётся писать в боевые
файлы, но для проверки слоя памяти теперь работает более чистый подход.

**Побочная польза.** Валидатор можно направить на любой каталог — удобно
при отладке на чужой копии проекта.

**Цена.** Копируется структура (`AGENTS.md`, `docs/`, `scripts/`,
`backend/`) во временный каталог перед каждым прогоном. Для небольших
тестов это доли секунды.

## ADR-019: Bootstrap-админ без пароля не создаётся

**Контекст.** Пароль по умолчанию `admin12345` лежал в `config.py` и в
`.env.example`. Развёрнутая копия проекта поднималась с известным паролем
и открытым в интернет портом — классическая дыра.

**Решение.** `bootstrap_admin_password` по умолчанию пустой. Seed создаёт
админа только если пароль задан; иначе пишет предупреждение в лог и
продолжает работу.

**Последствия.** Свежая установка требует явно задать пароль в `.env` —
одна лишняя строка при развёртывании, зато нет молчаливого дефолта.
Существующий админ при этом не трогается: seed ищет его по email и не
пересоздаёт.

**Побочно исправлено.** Из боевого `.env` убран дефолтный пароль: если
админ когда-нибудь удалится, seed напишет предупреждение, а не создаст
его заново с известным паролем.

**Когда пересмотреть.** Если появится нормальная установочная команда
(например, управляющий скрипт для создания админа), этот механизм
заменится ею.

## ADR-020: Три способа записи файлов из оболочки

**Контекст.** За сессию 2026-09-21 четыре скрипта пропали из-за
сорвавшегося heredoc. Конструкция с вложенными тройными кавычками не
находит закрывающий маркер, а `cat` с длинным телом рвётся аналогично.
Ошибка молчаливая: файл остаётся пустым или обрезанным.

**Решение.** Зафиксировать три рабочих приёма (подробности в
`docs/memory/CONVENTIONS.md`):

1. `printf` построчно — не зависит от разбора heredoc вовсе.
2. `cat` с коротким уникальным маркером — для простого тела.
3. `sed` или Python-скрипт — для правок существующих файлов.

**Обязательное правило.** Сразу после записи проверить, что файл создан
и содержимое разбирается: `ls -la` плюс проверка синтаксиса для Python.

**Последствия.** Пропажа скриптов перестала быть незаметной. Ошибка
обнаруживается за секунду, а не после того, как правка не сработала.

**Принцип.** Инструмент, который может сломаться молча, требует проверки
результата. Проверять надо сразу, а не когда последствия накопятся.

## ADR-021: Второй флоу подключения VK — отдельный модуль с общим сохранением

**Контекст.** Раньше группу ВК подключали вручную: админ создавал ключ в
настройках группы и вставлял его вместе с ID в форму. Задача — добавить
подключение через VK OAuth, не сломав ручной путь.

**Решение.** Два независимых входа, один путь сохранения:

- флоу определяет, какими кредами подключаемся, и передаёт их в общий
  `save_vk_channel`;
- сохранение (включение Long Poll, защита от дубля имени, `webhook_secret`)
  живёт в одном месте, поэтому оба флоу ведут себя одинаково;
- OAuth реализован как отдельный сервис и роутер, а не ветка «if oauth else
  manual» внутри существующей ручки.

**Про community token.** OAuth выдаёт пользовательский токен, а для приёма
сообщений обычно нужен токен сообщества, и через OAuth он не выдаётся. Флоу
поэтому гибридный: OAuth выбирает группу из списка сообществ админа, а если
VK требует ключ группы (коды 15/27) — канал не создаётся молча, форма ручного
ввода открывается с уже подставленным ID группы. Остаётся вставить только ключ.

**Безопасность.** `client_secret` живёт только в `.env` на сервере и в обмене
`code → token`. Токен пользователя не отдаётся браузеру: между callback и
выбором группы он хранится в короткоживущем серверном тикете. `state` —
подписанный JWT с одноразовым `jti`; сервис работает в один воркер, поэтому
хранилища хватает в памяти.

**Последствия.** Ручной флоу не тронут: те же проверки, те же ответы. Новый
флоу добавляет зависимость от настроек приложения на dev.vk.com (точный
`redirect_uri`). Если VK начнёт выдавать community-токены по OAuth, шаг с
ручным ключом можно будет убрать — остальное не изменится.

**Когда пересмотреть.** Если появится несколько воркеров, серверные тикеты и
список использованных `state` надо вынести в общее хранилище (БД или Redis):
сейчас они в памяти процесса.

## ADR-022: Один тип приложения VK ID и community-токен; список групп отложен

**Контекст.** Первый флоу (ADR-021) строился на классическом приложении
dev.vk.com: user-токен через OAuth плюс `groups.get?filter=admin` для списка
сообществ. На практике оказалось неверно:

- старое приложение отключено (`application is disabled`);
- приложение VK ID (`54786450`) — другого типа: `scope=manage` без `group_ids`
  даёт `Security Error`, а право `groups` оно запрашивать не умеет вообще
  (VK выдаёт его только по заявке в `devsupport@corp.vk.com`).

То есть «выбор группы из списка» этим приложением невыполним в принципе.

**Решение.** Перейти на штатный для VK ID **Authorization Code Flow для
получения токена сообщества**: `group_ids` передаётся сразу, а VK возвращает
`{group_id, access_token}` — community-токен с `expires_in = 0` (бессрочный).
Админ указывает одну группу ссылкой (`vk.com/club123`, короткое имя) или
числовым id; сервер превращает ссылку в число и кладёт его в подписанный
`state`. Callback обменивает код, берёт нужный токен и сохраняет канал через
тот же `save_vk_channel`, что и ручную форму.

**Что это даёт.** Ручной шаг с ключом группы больше не нужен: OAuth отдаёт
именно community-токен, который требует адаптер. Пропала и зависимость от
«нужен ключ группы» из ADR-021 — ошибки 15/27 на этом пути не возникают.
Источник токена для остального кода по-прежнему неразличим.

**Цена.** Выбор из списка сообществ отложен до получения права `groups`
(заявка в `devsupport@corp.vk.com`). Ссылки с коротким именем требуют
сервисный ключ приложения (`utils.resolveScreenName` без токена не работает
в API 5.199); числовые ссылки обходятся без него.

**Что отменено.** Промежуточный вариант с тикетами и модалкой выбора группы
(ADR-021, итерация 009) удалён вместе с эндпоинтами `groups` и `connect`:
он опирался на `groups.get`, которого у приложения нет.

**Когда пересмотреть.** Как только VK выдаст право `groups` — вернуть
автоподбор сообществ, оставив community-flow основным.
