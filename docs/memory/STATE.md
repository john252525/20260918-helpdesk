# Текущее состояние

Обновлено: 2026-09-24 (итерация 014)

## Работает

**Ядро.** Единый инбокс для трёх каналов, ответы из интерфейса, таймлайн событий. Сообщение сохраняется всегда, даже при недоступном провайдере.

**Мультитенант.** Компании (`workspaces`), три роли, изоляция данных проверена на двух компаниях живым тестом. Чужие данные отдают `404`.

**Каналы VK.** Две рабочие группы подключены и слушаются. Long Poll с сохранением курсора — перезапуск сервиса сообщений не теряет. Приём и отправка используют один и тот же токен (ключ группы, если задан): так отзыв OAuth-токена в настройках сообщества не роняет приём.

**Подключение VK через OAuth.** Рядом с ручной формой — поле «Ссылка на группу ВК» и кнопка «Подключить через ВК». Приложение VK ID (его `client_id` — в `VK_APP_ID`, `backend/.env`) получает **community-токен** группы и сохраняет канал автоматически.

**Ограничение VK ID: отправка.** Токен из OAuth принимает входящие (Long Poll), но VK отклоняет его на всех `messages.*` (ошибка 1051 «метод недоступен для этого профиля»), хотя права `messages`+`manage` выданы. Поэтому к таким каналам отдельным шагом привязывается **ключ группы** — он идёт в `config.send_token` и используется для ответов. Приём при этом не страдает. Ручной флоу (ключ сразу) работает как раньше.

**Канал WhatsApp с провайдерами.** Тип `whatsapp` обслуживает несколько вендоров: `config.provider` выбирает реализацию. Есть `touch-api` (визард: найти аккаунты по токену, создать/выбрать, вход по QR, автрегистрация вебхука) и `custom` (прежняя generic-форма; она же — фолбэк для старых каналов). Приём идёт через провайдерский `normalize_inbound`, статусы доставки обновляют `Message`. Список вендоров отдаёт бэкенд (`GET /channels/whatsapp/providers`). QR-код отдаётся через наш прокси (`qr-image`), токен вендора в браузер не попадает. Исходящие адресуются по вендорскому `thread` (`...@lid`), вердикт доставки читается из `results[]`, а не из общего `status`. Сообщения, отправленные с телефона, приходят вебхуком с `outgoing: true` и попадают в переписку как ответ команды (эхо своих ответов распознаётся по id).

**Единый публичный адрес.** `PUBLIC_BASE_URL` задаёт и URL вебхуков (VK, WhatsApp), и `redirect_uri` VK OAuth. Переезд dev → prod — правка одной строки в `backend/.env`. При повторном входе в WhatsApp вебхук перерегистрируется на текущий адрес.

**Управление WhatsApp-каналом.** В списке каналов видны аккаунт и статус вендора (шаг авторизации), статусы тянутся одним батч-запросом на токен (`POST /channels/whatsapp/status`) и обновляются кнопкой. По «Управление» открывается модалка с логином, QR и кнопками «Обновить», «Рестарт» (forceStop+getNewProxy+setState) и «Сброс» (плюс clearSession). Длительные операции идут в фоне (`POST /channels/whatsapp/maintenance`), прогресс виден в `config.maintenance`.

**Управление через UI.** Создание компании, сотрудники, подключение и удаление каналов, удаление компании, смена пароля, правка данных клиента, журнал вебхуков.

**Безопасность.** Неперебираемые URL вебхуков, журнал вебхуков за авторизацией, файлы с секретами `chmod 600`. Bootstrap-админ без явного пароля в `.env` не создаётся — нет молчаливого дефолта.

**Слой памяти и проверки.** Репозиторий git, `pre-commit` хук прогоняет четыре проверки: слой памяти, тесты валидатора, импорт бэкенда, синтаксис фронтенда. Валидатор `scripts/check_docs.py` принимает `--root` параметром. Тесты (`scripts/test_check_docs.py`) работают на копии во временной папке, боевые документы не трогают.

**Логи.** Ротация настроена, токены в логи не пишутся, ошибок нет.

## Следующее

В порядке приоритета:

1. **WhatsApp: сквозная проверка на живом номере.** Визард и приём проверены на тестовом токене; осталось отсканировать QR реальным телефоном и убедиться, что входящее долетает до инбокса, а ответ уходит. Нужен внешний `PUBLIC_BASE_URL`, чтобы вендор достучался до нашего вебхука.
2. **Мониторинг живости WhatsApp-сессии.** Периодически опрашивать `getInfo`: оборванная сессия сейчас обнаружится только по отсутствию сообщений.
3. **Сквозная проверка ответа на боевой группе VK.** Владелец привязывает ключ группы к OAuth-каналу и отвечает из интерфейса живому собеседнику. Механика проверена, полный путь оператора — нет.
4. **Написать в `devsupport@corp.vk.com`** про 1051 на community-токенах (текст согласован, отправляет владелец) и заодно про право `groups`. См. BACKLOG.
5. **Callback API как альтернатива Long Poll** — переключатель на канал. Нужен при росте больше 10–15 компаний: сейчас поток на каждый канал, а VK ограничивает число подключений к одной группе.
6. **Редактирование канала** — сейчас из UI только вкл/выкл, креды не поменять.
7. **Auto-reply не должен портить FRT** — сейчас автоответ бота засчитывается как первый ответ оператора. Ждём от заказчика точный список текстов автоответов.
